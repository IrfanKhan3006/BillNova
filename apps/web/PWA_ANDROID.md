# Installable app (PWA today, Play Store later)

The same approach TouristLeader used: make the site a proper installable web
app first, then wrap that app in a thin Android shell for Play. Nothing about
the server, the API or the billing logic changes in either step.

## What is live now (Phase 1 — PWA)

| Piece | Where |
| --- | --- |
| Web app manifest | `app/manifest.ts` → served at `/manifest.webmanifest` |
| Icons (192, 512, maskable 512) | `public/icons/` — **live-only**, generated from the live logo, like the favicon |
| Service worker | `public/sw.js` (registered by `app/components/ServiceWorker.tsx`) |
| Offline page | `public/offline.html` |
| Install button | `app/components/InstallAppButton.tsx`, shown in the sidebar and the mobile drawer |
| Status bar / notch handling | `viewport` in `app/layout.tsx` + `env(safe-area-inset-*)` padding in `SidebarLayout.tsx` |
| Product name | `app/lib/brand.ts`, overridden live by `NEXT_PUBLIC_BRAND_NAME=BillCraft` in `deploy/web-new/.env.production` |

The service worker is deliberately conservative: `/api/*`, every non-GET and
every cross-origin request go straight to the network, so no invoice, payment
or stock figure is ever served from a cache. Only Next's content-hashed
`/_next/static` output and the icons are cached, plus an offline fallback page.

`NEXT_PUBLIC_*` values are baked in at build time — changing the brand name on
the server without rebuilding does nothing.

## Phase 2 — Android app on Play (not done yet)

Same tooling as TouristLeader: a Trusted Web Activity generated by Bubblewrap,
which produces a real signed `.aab` that runs the live site full screen with no
browser UI.

1. `npx @bubblewrap/cli init --manifest https://billcrafts.com/manifest.webmanifest`
2. Package id: suggest `com.billcrafts.app`. Keep the keystore safe — losing it
   means never being able to update the listing again.
3. `npx @bubblewrap/cli build` → `app-release-bundle.aab`
4. Publish `/.well-known/assetlinks.json` on billcrafts.com with the signing
   key's SHA-256 fingerprint. **Without this the app opens with an address bar**,
   which is what makes a TWA look like a browser instead of an app.
5. Play Console: developer account (one-time fee), store listing, privacy
   policy URL, data-safety form, then upload the `.aab`.

Things to decide before Phase 2:

- **Push notifications** do not work reliably in a TWA. If push is required
  (payment reminders, for example), the shell has to be Capacitor + FCM
  instead, and that choice is cheaper to make before the Play listing exists.
- **iOS has no TWA equivalent.** iPhone users install through Safari's *Add to
  Home Screen*; the install button already detects iOS and shows those steps.
- Play requires a reachable **privacy policy page** — billcrafts.com does not
  have one yet.
